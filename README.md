# Pava OS

Internal operating system for Pava Steel Hardware — a single-tenant business
tool covering the full sales/inventory/customer lifecycle for a steel and
hardware retailer. Not a SaaS product; built for one business, used daily by
its own staff.

## What it does today

Add a product with real dimensions (gauge, thickness, shape) → receive
physical stock against it at a real acquisition cost → search for it by
trade terms a non-technical staff member would actually use → sell it
through a fast POS terminal or a formal quote-to-invoice flow → the sale
consumes stock FIFO, posts to a customer's credit ledger if applicable,
prints a proper numbered receipt, and shows up on a dashboard that looks
different depending on who's logged in.

## Stack

- **API**: NestJS 12 + Prisma 7 + PostgreSQL, hand-authored SQL migrations
  (see [Migrations](#migrations) below — this matters)
- **Web**: Next.js 16 (App Router) + Tailwind CSS 4 + `lucide-react` +
  `recharts`
- **Auth**: JWT access tokens + opaque refresh tokens tracked server-side in
  a `Session` table (real revocation, sliding inactivity timeout — see
  [Auth model](#auth-model))

## Repo structure

```
apps/api   → NestJS backend
  src/<module>/          one folder per domain module (products, inventory,
                          documents, customers, leads, contacts, users, ...)
  prisma/schema.prisma   the schema
  prisma/migrations/     hand-written SQL migrations, applied in folder-name order
apps/web   → Next.js frontend
  src/app/(app)/<route>/page.tsx   authenticated routes, share one layout/shell
  src/app/login/                   public login (staff PIN grid + admin form)
  src/components/<domain>/         forms, drawers, and detail views per module
  src/lib/<domain>-api.ts          typed fetch wrappers + shared types per module
  public/                          favicon, PWA icons, manifest.json
```

## Getting started

1. Provision Postgres and set `DATABASE_URL` in `apps/api/.env` (copy from
   `.env.example` in that folder — it also documents `JWT_SECRET`,
   `ADMIN_INACTIVITY_MINUTES`, `STAFF_INACTIVITY_MINUTES`, `SESSION_MAX_HOURS`).
2. `bun install` at the repo root (or `npm install` — both work; `bun.lock`
   is the tracked lockfile).
3. Apply migrations **in order** — see [Migrations](#migrations), this is
   not a normal `prisma migrate dev` project.
4. `bun run prisma:seed` — creates an admin account and two example staff
   accounts with different permission sets. Credentials are printed by the
   script.
5. `bun run dev:api` and `bun run dev:web` in separate terminals.
6. Set `NEXT_PUBLIC_API_URL` in `apps/web/.env` if the API isn't on
   `localhost:4000`.

## Migrations

**Every migration in this repo was hand-written, not generated by
`prisma migrate dev`.** That's a deliberate constraint carried over from how
this project was built (in an environment without access to
`binaries.prisma.sh`, which `prisma generate`/`migrate` need to download
engine binaries). Each migration folder's SQL was verified by hand against a
real Postgres instance before being added.

**Consequence for you:** don't run `prisma migrate dev` expecting it to
"just work" against this history — it will try to diff your schema against
what it thinks the migration history represents, and since that history
wasn't generated by itself, it may propose destructive or redundant changes.
Prefer `prisma migrate deploy` (applies pending migrations without diffing)
for existing databases, and `prisma migrate dev` only once you're confident
you understand what it's about to do — read the confirmation prompt.

Migration order matters and is encoded in the folder name's timestamp
prefix. As of writing there are 11, taking a fresh database from nothing to
the full current schema, including two schema *corrections* worth knowing
about if you're reading old migrations for context:

- `20260909090000_leads_contacts_split` — the original `Contact` model was
  actually shaped like a sales lead (it had `source` and `followUpAt`, no
  real contact-book fields). It was renamed to `Lead` (data preserved) and a
  new, real `Contact` model was added for the operational phone book
  (suppliers, drivers, technicians). If you're looking for the old
  `Contact` API, it's `/leads` now.
- Document numbering (`quoteNumber`/`invoiceNumber`/`receiptNumber`) and the
  `BusinessSetting` singleton table were added in
  `20260909130000_settings_and_document_numbering`.

## Auth model

Two tiers, not a role hierarchy:

- **Admin** — email + password, unlimited access, 30-minute inactivity
  timeout.
- **Staff** — 4-digit PIN, selected from an avatar-tile grid on the login
  screen, granular per-module permissions (see `Module` enum in
  `schema.prisma`), 60-minute inactivity timeout.

Access tokens are short-lived (15 min default) and silently refreshed by the
frontend. The thing that actually enforces the inactivity timeout is a
`Session` row's `lastActiveAt`, checked server-side on every `/auth/refresh`
call — not the JWT's own expiry. Logging out, or an admin resetting a
staff member's PIN, revokes the `Session` row, which is real revocation
(unlike a bare JWT, which can't be un-issued).

Permission checks are enforced by `PermissionsGuard` +
`@Permissions(Module.X)` on individual routes — **always server-side**. The
frontend's `hasPermission()` only controls what's rendered; treat any
frontend-only check as a UX nicety, never as the actual security boundary.

## Core financial/data invariants

These are load-bearing assumptions throughout the codebase. Breaking them
will corrupt historical data or accounting:

- **Documents are immutable once finalized.** `DocumentItem` freezes its own
  `unitPrice`, `basePrice`, `discount`, `lineTotal` at creation. There is no
  edit endpoint on a finalized document — only status transitions
  (quote → invoice → paid, or cancel).
- **Inventory cost ≠ selling price.** `Product.basePrice` is the one current
  selling price. `InventoryBatch.unitCost` is a historical acquisition cost,
  one row per delivery, consumed oldest-first (FIFO) via
  `InventoryService.consumeFifo`.
- **`Product.stockQuantity` and `Customer.creditBalance` are caches**, not
  sources of truth. The real record is the `InventoryMovement` ledger and
  the `CustomerLedgerEntry` ledger respectively. Never update either cached
  field directly — always through a ledger-writing method, in the same
  transaction.
- **Transport and commercial rounding are never silently absorbed.**
  `DocumentItem.transportAllocated` and `.roundingAdjustment` record exactly
  what was added to a line and why, even when the customer-facing price
  looks like a single round number.

## Branding

`public/logo.svg` is the source-of-truth mark (a geometric square-in-square
motif with a stroke-built "P", not a rendered typeface glyph). Favicon and
PWA icons in `public/` are pre-rendered from it — if you ever change the
mark, regenerate them (`rsvg-convert` + `imagemagick`, sizes: 16/32/48 for
`favicon.ico`, 180 for `apple-touch-icon.png`, 192/512 regular +
192/512 maskable for `manifest.json`).

## A note on how this codebase was built

Large parts of this system were built incrementally across many sessions,
verifying each change against a real (if disposable) Postgres instance
rather than trusting untested SQL. If you're extending it, the existing
module structure (one NestJS module + matching frontend `lib/<x>-api.ts` +
`components/<x>/` per domain) is the intended pattern to keep following.
